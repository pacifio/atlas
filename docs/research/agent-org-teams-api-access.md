**Date:** 2026-09-26. **Branch:** `feat/agent-ui-actions` @ `de679f07`. **Server reference:** `/Users/eemong/Codes/atlas-server-ref` working tree @ `e37ea88` (2026-09-11); server facts re-verified against `origin/main` @ `7717656` (2026-09-24) in §5.4.

**Question.** The user wants a third in-process tool server (after memory, ADR-0010, and UI, ADR-0012) through which the native agent reads the Organisation's timeline, comments, channels and members, and acts on the user's behalf (DM a member, post to a channel, create a page in a Space, resolve a comment), asks clarifying questions, and respects roles. What actually exists today on the client, the engine and the server?

**Sources.** Primary only: Rust under `crates/`, `src-tauri/src/`, `vendor/atlas-engine/`; TypeScript under `src/`; ADRs under `docs/adr/`; the server monorepo's route handlers, zod contracts and DB schema. ## Summary

**Re-verification note (2026-09-26).** The server facts in §5 were re-checked against `origin/main` @ `7717656` (39 commits ahead of the `e37ea88` working tree, read only via `git show`/`git grep`, nothing executed). `origin/main` serves every route the desktop codes against, plus keyword search (`q`), an inbox with mark-read, and chat `artifact_refs` to a Session/Checkpoint — see §5.4. Still absent on `origin/main`: any author/date filter on the board, any per-member metrics, any service token. §3 (org routes, roles, usage) and §4 (chat/spaces) were spot-checked and stand, with one change: ingest no longer has `PUSH_ROLES`; access is per-Workspace, not per-role (§5.4.5).

Five findings shape everything downstream. (1) **The server reference working tree is stale relative to the client, but `origin/main` is not.** The desktop codes against `GET /sessions`, `GET /sessions/{project}/{session}`, `/comments` with `PATCH {resolved}`, a per-Project WebSocket with `session.subscribe`/`comment.upsert`, and four artifact types (`agent_session`, `agent_message`, `tool_call`, `checkpoint`); the `e37ea88` checkout's ingest worker accepts only `agent_message | memory_fact | kb_item | git_ref`, writes no DB rows, and has no read, search or comment routes (§5.3). All of these now exist on `origin/main` and match the client's contract (§5.4); the remaining unverified items are listed at the end of §5.4. (2) **The tool-server seam is fully reusable.** A third MCP service mounts on the same loopback listener behind the same per-session bearer token in one line (`MemoryServer::start_with(.., mounts)`), and the engine projects every Atlas-offered server as auto-approved and non-deferred (§1). (3) **Everything the agent would need to call the cloud is already reachable from Rust**: the account session token, `GET /token` → 10-minute EdDSA JWT, `atlas-comms` (chat REST + WS), `atlas-artifacts` (sessions/comments REST + WS) and `atlas-checkpoint::sync` (push) all live in Rust and hold the bearer; the renderer never sees a token (§2). (4) **Posting a message, DM or Space page is WebSocket-only server-side** (no REST send), the desktop already holds those sockets in Rust, and `<@user_id>` is the only mention form — there is no `#channel` reference and no name→id lookup route; the roster comes from `GET /organization/get-full-organization` (§4, §6). (5) **The engine has a `request_user_input` tool and an MCP elicitation path, and Atlas refuses both**: the native seam answers only the three approval requests and returns an error for `item/tool/requestUserInput` and `mcpServer/elicitation/request`; `request_user_input` is also gated to Plan collaboration mode upstream, which Atlas never sets (§7). Roles are `admin | product_owner | developer | member` (no `owner`), and the only per-member usage endpoint is AI request/weight counts for org admins — no tokens-by-member, no "code shipped" (§3).

## 1. Existing tool-server pattern (what a third server copies)

**Transport.** One axum listener bound to `127.0.0.1:0`, serving rmcp `StreamableHttpService` (streamable HTTP MCP) — `src-tauri/src/commands/memory_server/host.rs:59-97`. The memory service is nested at `MCP_PATH = "/mcp"` (`memory_server/mod.rs:48-49`); other services are passed in as `mounts: Vec<axum::Router>` and merged onto the same router before the token middleware wraps everything (`host.rs:79-84`, comment at `host.rs:60-66`: "One listener means one token per session covers every service: the token table holds one token per session, so a second would revoke the first"). The UI server is such a mount at `UI_PATH = "/ui"` (`ui_server/mod.rs:44`, `ui_server/tools.rs:227-235`). `MemoryServerHost::url_at(path)` gives a mounted service's URL (`host.rs:107-109`, `host.rs:155-157`).

**Token.** One bearer per session, `Grant { session_id, agent, cwd }` (`memory_server/tokens.rs:27-34`). The offer mints an *unbound* token before the session id exists (`tokens.rs:79-90`), the offer's settle closure binds it to the id the agent answers with or revokes it (`memory_server/offers.rs:117-131`), and the `SessionLifecycle` hook (`src-tauri/src/commands/agent_host.rs:272-276`) mints on `session_started` / revokes on `session_ended` (`tokens.rs:133-160`). The middleware `require_token` reads `Authorization: Bearer <token>`, looks it up, and inserts the `Grant` into request extensions (`tokens.rs:164-186`); a tool handler reads it back from the axum `Parts` (`ui_server/tools.rs:212-219`). So **every tool call already knows which session, which agent id and which launch directory it is for** — but not which user or org (the Grant has no org field; the org is resolved app-wide, §2).

**Offer / gating.** `SessionMcpRequest { agent_id, http_mcp, ui_control, cwd, session_id }` (`crates/atlas-agent-servers/src/session_mcp.rs:26-41`) is what a connection asks the host with; the host answers via the `SessionMcpServers` trait (`session_mcp.rs:45-47`) installed on `AgentHost` (`src-tauri/src/commands/agents.rs:694-697`). The one implementation, `MemorySessionOffers`, decides both servers and mints **one** token for whichever are included (`offers.rs:80-132`). Decision tables: memory = `http_mcp && sharing_on && server_running` (`offers.rs:42-52`); UI = `http_mcp && ui_control && navigation_on && server_running` (`ui_server/offers.rs:23-35`). `ui_control` is set `true` only by the in-process native connection (`crates/atlas-native-agent/src/engine/connection.rs:682-685`) and `false` by ACP (`crates/atlas-agent-servers/src/connection.rs:472-476`). The UI `NavigationGate` reads the `agent_ui_navigation` setting on every offer *and* every call (`agents.rs:679-687`, `ui_server/tools.rs:171-173`). A third server would add a third decision in `offers.rs::offer` and push a third `(name, url)` entry onto the same token.

**Engine projection.** For the native agent the offered `acp::McpServer::Http` entries become per-thread config overrides `mcp_servers.<name>.{url, http_headers, default_tools_approval_mode="approve", omit_tools_from=["deferred"]}` (`crates/atlas-native-agent/src/engine/mcp.rs:36-58`). The module doc says why both standings exist and that they are load-bearing: "everything projected here is a server Atlas itself offers. A user-configured HTTP server would inherit them" (`mcp.rs:11-30`). The engine resolves `default_tools_approval_mode` per server in `custom_mcp_tool_approval_mode` (`vendor/atlas-engine/core/src/mcp_tool_call.rs:1127-1153`); `AppToolApproval` is `Auto | Prompt | Writes | Approve` (`vendor/atlas-engine/config/src/mcp_types.rs:26-32`). Tool names reach the model as `mcp__<server>__<tool>` (`ui_server/mod.rs:40-41`).

**Instructions / protocol text.** Each service returns its `INSTRUCTIONS` in `ServerInfo::with_instructions` (`ui_server/tools.rs:200-202`; memory's is `memory_server::INSTRUCTIONS`, `mod.rs:44`). ADR-0010 states the engine shows this as the description of the tool namespace (`docs/adr/0010-shared-memory-is-pulled-through-the-tool-server.md`, "Context", last paragraph). Tool schemas are hand-built `Tool::new(name, description, json_schema)` (`ui_server/tools.rs:50-53`), kept flat because "every native turn carries them in its fixed prefix" (`tools.rs:5-7`; ADR-0012 "Consequences": ~1.8 KB for seven tools).

**Call handling.** `ServerHandler::call_tool` → `dispatch(grant, request)` → for UI, one `UiRequest` emitted as Tauri event `atlas:ui-action` and answered by `ui_action_respond` within `UI_ACTION_TIMEOUT` (`ui_server/tools.rs:169-196`, `ui_server/mod.rs:46-58`). Memory tools instead call the store directly in Rust (`memory_server/tools.rs`). **An org server has a third option neither uses yet: call the cloud from Rust inside the tool handler** (§2).

**Wiring site.** `src-tauri/src/commands/agents.rs:651-743` builds host, gate, UI bridge, navigation gate, `MemorySessionOffers::new(..).with_ui(..)`, index/bootstrap/evict sources, and calls `server.start(memory, gate, sources, vec![ui_router])` (`agents.rs:734-743`).

## 2. Cloud auth from the client

**Credential.** Device-authorization grant against `DEFAULT_AUTH_BASE = "https://auth.tryatlas.cc/api/auth"` (`src-tauri/src/auth/config.rs:18`, env `ATLAS_AUTH_URL` override only, no on-disk override by design, `config.rs:1-13`). The stored credential is the Better Auth **session token**, persisted at `<config_dir>/atlas-session.json` (`src-tauri/src/auth/store.rs:4`). Server side: `POST /device/code`, browser `/device`, `POST /device/token` returns an opaque session token; no separate refresh token (`server:apps/auth/src/auth.ts:499-504`, `server:docs/api/atlas-auth-api.md:248-270` — the latter is a doc, **unverified against a handler**).

**Access JWT.** `AuthCore::mint_access_token` = `GET /token` with the session token as Bearer → `{ token }` (`src-tauri/src/auth/core.rs:1293-1307`, `authed_get` at `core.rs:786`). Server: jwt plugin, **EdDSA** (not RS256 — `server:apps/auth/src/auth.ts:466`, verifier pins `algorithms: ["EdDSA"]` at `server:packages/auth-client/src/index.ts:163`), TTL `ACCESS_TOKEN_TTL = "10m"` (`auth.ts:105`), claims `iss, aud="atlas", sub=userId, orgs: {orgId: Role}` (`auth.ts:475-493`, `auth-client/src/index.ts:16-19`). The client reads `orgs` off the JWT without verifying the signature to label roles (`core.rs:1560-1575` doc comment). Refresh = mint again (sync drains refresh once per drain on 401, `crates/atlas-checkpoint/src/sync.rs:26-33`).

**Who holds the bearer: Rust only.** Three `TokenSource` impls, all closures over `AuthState.core().mint_access_token()`: engine gateway `AccountTokenSource` (`src-tauri/src/commands/agents.rs:2007-2015`), chat `AppTokenSource` (`src-tauri/src/commands/comms.rs:35-60`), artifacts `AppTokenSource` (`src-tauri/src/commands/artifacts_cloud.rs:70-91`). `atlas-comms` states the rule: "the renderer never holds one, which means it can neither open the socket nor make a REST call … The renderer is therefore a projection" (`crates/atlas-comms/src/lib.rs:6-14`). `RestClient` caches a minted JWT for `TOKEN_REUSE = 240 s` because `GET /token` is rate-limited (`crates/atlas-comms/src/rest.rs:93-97, 108-125`); `atlas-artifacts` does the same (`crates/atlas-artifacts/src/client.rs:328-340`).

**Base URLs (Rust constants).** Chat `https://chat.tryatlas.cc` (`crates/atlas-comms/src/lib.rs:71`), ingest `https://ingest.tryatlas.cc` (`crates/atlas-artifacts/src/lib.rs:64`; `crates/atlas-checkpoint/src/sync.rs:69-80`), web link `session_web_url` → `{web}/timeline?org=&workspace=&session=` (`crates/atlas-artifacts/src/lib.rs:125-130`). Server host map (`server:apps/*/wrangler.jsonc`): web `app.tryatlas.cc`, auth `auth.tryatlas.cc`, ai `ai.tryatlas.cc`, ingest `ingest.tryatlas.cc`, sync `sync.tryatlas.cc`, chat `chat.tryatlas.cc`.

**How a request is scoped to an org.** Chat REST appends `?org=<orgId>` to every path and sends `Authorization: Bearer <jwt>` (`rest.rs:137-157`); the server's `verifiedCaller` 400s without `org`, 401s without a valid JWT, 403s a non-member (`server:apps/chat/src/index.ts:87-109`). Artifacts REST uses `.query(("org", org_id))` (`client.rs:96-107`). WebSockets carry the JWT as `Sec-WebSocket-Protocol: atlas.v1, atlas.ticket.<jwt>` (`crates/atlas-comms/src/conn.rs:10`, `crates/atlas-artifacts/src/socket.rs:13`; server `server:packages/do-protocol/src/upgrade.ts:100-132`). The gateway path sends `atlas-org: <orgId>` (`vendor/atlas-engine/core/src/client.rs:1508-1510`, org supplied by `set_org_source` = `AuthSnapshot::SignedIn.active_org_id`, `agents.rs:957-969`).

**Two org ids.** `AuthSnapshot::SignedIn` carries both `active_org_id` (billing/display, falls back to the first org) and `comms_org_id` (explicit choice; `None` for a local-only org). Chat retargets on `comms_org_id`, never `active_org_id` (`src-tauri/src/commands/comms.rs:176-215`, esp. `200-206`). Artifacts targets `ArtifactsCloudState.org` set by `artifacts_cloud_retarget(org_id, project_paths)` from the renderer (`artifacts_cloud.rs:249-260`). **An org tool server must pick one of these, and today nothing hands a per-session org to a tool** (the `Grant` has none, §1).

**Reachable from Rust vs TS.** All HTTP/WS clients are Rust crates with no Tauri dependency (`atlas-comms`, `atlas-artifacts`, `atlas-checkpoint::sync`) plus the `AuthCore` org calls in `src-tauri/src/auth/core.rs`. The TS side only invokes commands (`src/features/comms/lib/comms-api.ts`, `src/features/artifacts/lib/comments-api.ts:83-119`, `src/features/auth/lib/auth-api.ts`). Nothing an org tool server needs is TS-only.

## 3. Org API surface (server) and roles

**Routes.** No custom Atlas org REST code exists; the org API is Better Auth's `organization()` plugin mounted by `auth.handler` (`server:apps/auth/src/index.ts:140`, configured `server:apps/auth/src/auth.ts:355-464`). Paths, all under `/api/auth/organization/` and all called by the desktop's `AuthCore` (Rust):

| Route | Desktop caller | Notes |
|---|---|---|
| `GET list` | `core.rs:503` | only source of org names |
| `POST create`, `POST check-slug`, `POST delete` | `core.rs:913, 949, 980` | |
| `GET get-full-organization?organizationId=` | `core.rs:1012-1093` (`list_members`) | `members[{id, role, createdAt, user{id,name,email,image}}]` → `OrgMember { id (membership id), user_id, name, email, role, created_at, avatar_path }` (`core.rs:1534-1548`) |
| `GET list-invitations`, `POST invite-member`, `POST cancel-invitation`, `POST update-member-role`, `POST remove-member` | `core.rs:1095, 1141, 1204, 1220, 1252` | invitations are admin-scoped (`core.rs:1097-1099`) |

Auth for these = Better Auth session (cookie + Origin, or `Authorization: Bearer <session token>` via the `bearer()` plugin, `server:auth.ts:505-508`). The desktop sends the session token (`core.rs:779-786`). There are **no zod contracts** for these routes; typed shapes exist only in `server:apps/web/src/lib/api.ts:95-128`. **No teams:** the plugin's teams feature is not enabled and there is no `team` table (`server:packages/db/src/auth.schema.ts`; "team" appears only in a Better Auth comment at `server:apps/auth/src/access.ts:16`).

**Role model.** `Role = z.enum(["admin", "product_owner", "developer", "member"])` (`server:packages/contracts/src/role.ts:9`); client mirror `Role { Admin, ProductOwner, Developer, Member }` with `from_claim` dropping unknowns (`src-tauri/src/auth/store.rs:47-73`). **There is no `owner`.** Creator role is `admin` (`server:auth.ts:358`). DB `member.role` is free text default `"member"` (`server:auth.schema.ts:119-136`), normalised by `primaryRole` (`server:auth.ts:123-126`).

**Permission matrix** (`server:apps/auth/src/access.ts:15-70`): statements `sprint[read,manage]`, `issue[read,comment,work,manage]`, `doc[read,comment,edit,manage]`, `agent[read,push]`. `admin`: org update/delete, member CRUD, invitations, `agent[read]`; `product_owner`: `agent[read]`; `developer`: `agent[read,push]`; `member`: no `agent` permission.

**Enforcement.** (a) Org-management routes: inside Better Auth against `ac`/`roles`, no Atlas code. (b) JWT `orgs` claim + helpers `orgRole / isOrgMember / hasOrgRole` (`server:packages/auth-client/src/index.ts:188-208`). (c) DB-fresh `orgRole(env, orgId, userId)` (`server:auth.ts:142-156`), used by usage and capture. (d) Per worker: ingest `PUSH_ROLES = ["developer"]` via `hasOrgRole` → 403 otherwise (`server:apps/ingest/src/index.ts:30, 54-58`); ai = membership only; chat inline `conn.role === "admin"` checks (e.g. `server:apps/chat/src/chat-do.ts:2490, 5556, 5625`); sync DO role checks are a TODO (`server:apps/sync/src/org-do.ts:78`). (e) Platform admin is a separate env allowlist (`server:apps/auth/src/platform.ts:77-104`).

**Per-member usage.** `GET /api/auth/usage?orgId=&days=` (`server:apps/auth/src/org-usage.ts:33-103`): any member gets `own {days, byModel}`; only primary-role `admin` gets `org: UsageReport` with `ledger.members: UsageMember[] { userId, name, email, requests, weighted }` (`server:packages/contracts/src/console.ts:136-142, 152-179, 185-209`). SQL is `COUNT(*), SUM(weight_applied) GROUP BY user_id` (`server:apps/auth/src/usage.ts:260-270`). **No per-member token split, no per-member cost, retention about a quarter.** `GET ai.tryatlas.cc/v1/usage` returns only the caller's cap windows (`server:apps/ai/src/index.ts:606-623`). **Nothing exists for "code shipped"**, lines changed, commits per member, activity, leaderboards (greps over `server:apps/ packages/`: `leaderboard|code shipped|lines? (of code|changed)|loc_added|member performance|productivity|velocity` → no files; `\b(stats|metrics|analytics|activity)\b` → comments only). The desktop's own usage is local-only: `src-tauri/src/commands/usage.rs:1-40` ("Only sessions run through Atlas are counted"), from `atlas-checkpoint` token totals. The desktop **does** carry `insertions/deletions/files_touched/total_tokens` per remote session on the board row (`crates/atlas-artifacts/src/model.rs:70-84`) — a client could fold those per `author_id` (`model.rs:109`), but no server endpoint does.

**API keys / service tokens.** None (grep `api[_ -]?key|apiKey|personal access|service[_ -]?token|x-api-key` → only email-worker comments). The only non-human subject is `svc:atlas` over a Worker service binding, not HTTP (`server:apps/ai/src/index.ts:172, 1126-1161`). An agent acts strictly as the signed-in user.

## 5. Timeline / sessions / comments

### 5.1 Client data model and capture

`atlas-checkpoint` records per Project into `<project>/.atlas/sessions.db` (`docs/agents/timeline-gate.md`). Tables `agent_session`, `agent_message`, `turn`, `tool_call`, `checkpoint`. `Session { id, workspace_id, source: Source (Acp|Native), native_session_id, title, agent, model, branch, cwd, token_totals, started_at, updated_at, last_activity_at, needs_attention, redaction_counts, sync_state }` (`crates/atlas-checkpoint/src/model.rs:323-363`). `Binding { workspace_id, root, mode: ProjectMode (Local|Cloud), slug, org_id, root_commit_sha, git_url, enabled, import_approved, drain_state, remote_workspace_id, created_at }` (`model.rs:491-521`). The send path calls `CaptureState::note_prompt(session_id, cwd, plugin_id, model, raw text)` (`src-tauri/src/commands/capture.rs:538`, called from `agents.rs:1433, 1457`), which seeds a `SessionBinding` with `turn_seq` (`capture.rs:101-117`); `source_for(plugin_id)` maps `ATLAS_AGENT_ID` → `Source::Native` (`capture.rs:2553`). Deltas reach capture through `CaptureMiddleware` on the outbound pipeline (`agents.rs:88`).

**The "current session" join.** A live chat is keyed by its ACP session id; the captured row is found by `Store::session_id_for(workspace_id, source, native_session_id)` (`crates/atlas-checkpoint/src/store.rs:234-247`). `chat_comment_target(project_path, native_session_id)` does exactly this and returns `CommentTarget { remote_project_id (= binding.remote_workspace_id), session_id (captured row id = server id), entries: Vec<AnchorEntry> }`, `None` unless the org is targeted, the binding is `is_cloud_bound` (Cloud + enabled + same org) and the session has been captured (`src-tauri/src/commands/artifacts_cloud.rs:376-441`, added in `388e5e8e`). `AnchorEntry { row_id, kind, turn_seq, native_id, tool_name }` from `atlas_checkpoint::session_anchors` (`crates/atlas-checkpoint/src/timeline.rs`, `anchors()` added in `388e5e8e`; prompts carry a synthesised `prompt-{turn}-{hash}` native id). #### 5.4.3 The Workspace socket

`GET /ws?org=&workspace=`, JWT ticket in `Sec-WebSocket-Protocol` verified by the shared `authorizeWsUpgrade` (400 no org / 401 bad ticket / 403 non-member), Workspace resolved for its slug, then handed to the object (`apps/ingest/src/socket.ts:43-89`). One socket per **open Workspace**; the board keeps polling by design (`packages/contracts/src/artifacts-ws.ts:9-13`). **Client frames** (`artifacts-ws.ts:59-81`): `push { batch_id, artifacts[1..100] }` (mirrors `POST /ingest` row for row, `:22-28`), `session.subscribe { session_id }`, `session.unsubscribe` — the subscription is stored on the socket attachment (`workspace-do.ts:1967-1993`). **Server frames** (`artifacts-ws.ts:99-208`): `workspace.hello { protocol: 1, workspace_id, workspace_slug, org_id, online[] }` (`workspace-do.ts:1861-1872`); `artifact.upsert { session_id, change: inserted|updated, entry: TimelineEntry }` to subscribers of that Session only; `session.summary { summary: SessionSummary }` to **every** socket on the Workspace, including liveness flips (`workspace-do.ts:2519-2559`); `comment.upsert { session_id, comment }` for post/edit/resolve/delete alike, to subscribers, and to a guest socket only when the share's comments flag is on (`workspace-do.ts:1228-1234`); `presence { online[] }` replaced wholesale, guests excluded (`:2185-2199`); `push.result`; `error { batch_id?, status, code, message }`. Binary frames are refused (blobs stay on `PUT /blobs`, `:1940-1947`).

**`live` — the exact rule.** `live = source != "external_jsonl" && (now − updated_at) < 90 000 ms && (now − last_activity_at) < 3 600 000 ms`, where `updated_at` is when *this server* last wrote the Session and `last_activity_at` is the recording machine's newest artifact stamp (`workspace-reads.ts:281-293`; `SESSION_LIVE_WINDOW_MS = 90_000`, `SESSION_LIVE_ACTIVITY_WINDOW_MS = 60 * 60_000`, `sessions.ts:49, 74`, rationale `:38-73`). The flip **on** rides the write; the flip **off** is a Durable Object alarm scheduled `90 s + 1 s` after a write, which re-publishes `session.summary` only for Sessions whose flag changed (`session_live` table, `workspace-do.ts:2447-2510, 2519-2549`). So the client's belief in §5.2 is confirmed: the desktop never declares liveness.

**Revocation.** Access is re-asked of the D1 registry and the object's `revoked_members` table on every connect and every push, never read off the connection (`workspace-do.ts:1892-1929, 2055-2062`). Membership events reach ingest on a second queue, `atlas-artifact-events` (a Cloudflare queue has one consumer, so chat's cannot be shared; ADR-0014 :70-75; `index.ts:146-148`); the consumer fans out per Workspace and `revokeStaleSockets` / `cutMemberSockets` / `cutAllSockets` close with `1008` (`WS_CLOSE_REVOKED`, `artifacts-ws.ts:44`; `workspace-do.ts:2340-2432`); the registry's member/visibility routes and share revocation call `cutStaleSockets` best-effort after the write (`workspace-call.ts:142-158`).

#### 5.4.7 The server's vocabulary (origin/main `CONTEXT.md`, ADR-0014/0015/0016)

Quoted so the Atlas client's `CONTEXT.md` does not collide. **Workspace** — "a synced unit under an Organisation, named by a Slug … The org-level container, not a per-machine one … This is the thing the web app calls a *project*; the word on the wire and in this glossary is Workspace" (`CONTEXT.md:13-18`). **Project** — "local codebase directory on a member's machine. Not synced … Never the server-side aggregate" (`:22-24`). **Binding** — "the local association between one machine's Project directory and one Workspace. Per machine" (`:25-26`). **Session** — "one agent conversation recorded under a Workspace: who ran it, which agent and model, when it started, what it cost, and the stream of Messages, Tool Calls and Checkpoints it produced. The unit a person opens, links to, shares and comments on" (`:220-222`). **Checkpoint** — "the slice of one Session whose work landed in one git commit. Natural key (Session, commit SHA). Not a commit and not a snapshot: it is the *join*" (`:228-230`). **Entry** — prompt/response/thinking/tool call/checkpoint "as a reader sees it. Deliberately *not* a synonym for Artifact" (`:255-259`). **Author** — "Always derived from the verified token that pushed it, never read from the payload" (`:241-243`). **Comment** — "somebody's remark anchored to a Session or to one row inside it … Authored in the cloud — the one thing in this feature the desktop does not originate. Replies hang off a root Comment; a root can be **resolved**" (`:296-299`); **Anchor** (`:300-301`). **Live** — "a Session the server has written an Artifact for very recently *and* whose recorded activity is recent too. ## 6. Mentions and identity resolution

**Agent composer (chat with the agent).** `MentionData` kinds: `file, folder, symbol, knowledge, component, repo, workspace, branch, past_message, past_session` (`src/features/chat/lib/mentions.ts:62-175`, categories `:187-206`); Rust twin `MentionSpec` (`src-tauri/src/commands/compose_prompt.rs:30-115`) with `Workspace { id, display_name, abs_path, org_name }` (the `"workspace"` tag is a storage key for "project", `compose_prompt.rs:80-92`; `CONTEXT.md:26`) and `PastSession { id, display_name, session_title, inline_body }`. `compose_prompt` inlines bodies (32 KB cap) and emits `resourceLinks` (`compose_prompt.rs:1-22, 117-135`). `mention_search` is one Rust command over files/folders/symbols/knowledge/repos/branches (`src-tauri/src/commands/mention_search.rs:1-22`). **No member, channel, or remote-session mention kind exists**; a `@session:` mention is a *local* past transcript, not a cloud session id. Nothing carries a user id or conversation id into the prompt today.

**Team chat (comms).** Bodies store `<@user_id>`; `MENTION_SOURCE = "<@([A-Za-z0-9_.:-]{1,128})>"` and `parseMentions` mirror the server (`src/features/comms/types.ts:213-240`; server `chat.ts:726, 760-777`). Broadcasts are `@channel` / `@here` (server `chat.ts:735`, `MentionKind = user|channel|here`). The composer paints `<@id>` as a pill via CodeMirror (`src/features/comms/lib/cm-comms-mention.ts:1-16`). **`#channel` references do not exist** (server grep `<#|#channel|channel_mention` → one comment). The server parses mentions; a client cannot declare them.

**Name → id.** No server lookup route (server greps `/members`, `/users`, `listMembers`, `resolveUser|byEmail|directory` → only the Better Auth plugin). The directory is `GET /organization/get-full-organization` (§3), cached in `src/features/organisations/stores/members-store.ts` (30 s fresh) and exposed as `OrgDirectory` (`src/features/organisations/lib/use-org-directory.ts`, used by `chat-comments-store.ts:22`). From Rust, `AuthCore::list_members(org_id)` returns `OrgMember { user_id, name, email, role }` (`core.rs:1018-1093`) — enough for an org tool to resolve "@Member" by name/email in Rust, with ambiguity to disambiguate (§7). ## 7. Elicitation / clarifying-question path

**Engine.** A first-class tool `request_user_input` exists: `REQUEST_USER_INPUT_TOOL_NAME` and schema `{questions: [{id, header, question, options?: [{label, description}] }]}` with the client adding a free-form "Other" (`vendor/atlas-engine/core/src/tools/handlers/request_user_input_spec.rs:10-60`). Handler: root thread only (`request_user_input.rs:61-65`), **available only in collaboration modes where `ModeKind::allows_request_user_input()` — i.e. `Plan` — unless `Feature::DefaultModeRequestUserInput` is on** (`request_user_input.rs:67-70`; `vendor/atlas-engine/tools/src/tool_config.rs:39-47`; `vendor/atlas-engine/protocol/src/config_types.rs:682-684`). It blocks the turn on `session.request_user_input(..)` (`request_user_input.rs:76-89`) and surfaces to the app-server client as server request **`item/tool/requestUserInput`** (`vendor/atlas-engine/app-server-protocol/src/protocol/common.rs:1610-1613`). A parallel path exists for MCP servers: `mcpServer/elicitation/request` (`common.rs:1615-1618`), fed by rmcp `elicitation/create` handling in `vendor/atlas-engine/rmcp-client/src/elicitation_client_service.rs:1-60`.

**Native seam refuses both.** `crates/atlas-native-agent/src/engine/connection.rs:880-928` handles `CommandExecutionRequestApproval`, `FileChangeRequestApproval`, `PermissionsRequestApproval`; every other request ("Elicitations, dynamic tool calls, attestation") is answered with `Err("Atlas does not serve this engine request yet")`. `crates/atlas-native-agent/src/lib.rs:38-39`: "Elicitations. Nothing is asked of the user mid-turn except tool permission". `runtime.rs:241` sets `mcp_server_openai_form_elicitation: false`. Atlas maps its four modes to `AskForApproval`/`SandboxPolicy` only (`crates/atlas-native-agent/src/engine/modes.rs:1-60`); grep `collaboration_mode|CollaborationMode|ModeKind|Feature::` over `crates/atlas-native-agent/src` → nothing, so the engine's collaboration mode stays default and `request_user_input` would refuse even if the request were served.

**UI already exists (ACP path).** `SessionElicitation` renders a form elicitation whose schema looks like AskUserQuestion as a question card above the composer (same place as the permission card), otherwise `ElicitationModal` (`src/features/chat/components/session-elicitation.tsx:1-20`); decided by `elicitationQuestionForm` on the schema, "not on which agent sent it". Answered via `agents.respondElicitation` → `agents_respond_elicitation` (`src/features/chat/lib/agents-api.ts:159-165`; `src-tauri/src/commands/agents.rs:1088-1096`). Store/plumbing: `crates/atlas-acp-thread/src/elicitation.rs` (session- and request-scoped), `agent-elicitation-host.tsx` for sign-in questions. **So a clarifying question already has a renderer; what is missing is the native connection turning `item/tool/requestUserInput` (or an MCP `elicitation/create`) into an `acp::CreateElicitationRequest` on the thread, and enabling the tool.**

**Cheapest alternative that needs no engine change:** the tool returns the candidates as its result and the model asks in prose; the memory server's `INSTRUCTIONS` already rely on prose protocols (`memory_server/tools.rs`).

## 8. Consent / permission model for outward-facing calls

**Native agent approvals.** Three engine requests → Atlas's dialog with options `allow-once (AllowOnce) | allow-always (AllowAlways, "Allow for this session") | reject (RejectOnce)`, plus `Cancel` from dismissal (`crates/atlas-native-agent/src/engine/approvals.rs:1-25, 48-66, 72-90`). Which calls prompt is a function of the chat's permission mode: `default` "Prompt before edits and commands", `acceptEdits`, `plan` (read-only), `bypass` (`modes.rs:37-58`). Everything Atlas offers over MCP is **`default_tools_approval_mode = "approve"`** — never prompted, regardless of mode (`mcp.rs:52`; ADR-0012 "Auto-approved, behind one setting"). An org server mounted the same way would inherit "approve" unless its projection sets `Prompt`/`Writes` per tool (`mcp_types.rs:26-32`, per-tool `tools.<name>.approval_mode` read at `mcp_tool_call.rs:1147-1150`).

**What makes auto-approval acceptable today.** ADR-0012 keeps the UI surface non-destructive by rule (never sends in the caller's chat, never presses Enter, refuses unsaved close) and audits every call: one tool row in the chat and one row in the Logs panel (`src/features/ui-actions/lib/ui-actions.ts:4`; ADR-0012 "Consequences"). Both gates (sharing toggle, navigation setting) are checked at offer and on every call (`memory_server/host.rs:17-20`, `ui_server/tools.rs:171`).

**Consent record.** ADR-0006 is one paragraph: the company brain is "explicit, consent-based"; "DMs and private channels are excluded unless their participants explicitly add them" (`docs/adr/0006-consent-based-company-brain.md:3`). Capture for Cloud additionally requires `import_approved` from a disclosure confirmation (`model.rs:509-512`). Server-side, `GET/POST /api/auth/capture` gates changes to org admins (`server:apps/auth/src/capture.ts:77-87`).

**What a "send a DM" tool would inherit:** auto-approve, no prompt, only the connection-level gate (`ui_control`) and whatever setting the server's offer consults — i.e. **nothing per call unless the projection says `Prompt`** or the tool server itself raises an approval (the engine's `PermissionsRequestApproval` is a runtime-permission request, not a generic hook). The existing precedent for a per-call decision is the UI server's "a busy chat asks the user" (`ui_server/tools.rs:110`), implemented in the frontend action, not in the engine.
